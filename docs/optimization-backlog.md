## 三、播放加载性能

### 3.1 当前瓶颈与目标

当前链路为：解析片源 → 服务器下载完整一集 → FFmpeg 处理整集 → 返回播放地址 → 手机初始化和缓冲。

目标：未缓存集数不必等整集准备完；正常观看继续准备下一集。手机可以增加适度缓冲和磁盘占用，但不引入明显发热、内存增长或后台耗电。

### 3.2 先建立基线

- [ ] 记录片源解析、排队、下载、处理、首批可播放媒体数据、手机初始化及实际首帧耗时。
- [ ] 区分冷启动、手动跳集、已预加载连播、再次播放缓存内容。
- [ ] 分别测量服务器到片源、服务器到国内手机的网络表现。
- [ ] 两端分别记录 Wi-Fi、蜂窝及弱网表现；采集多次样本，报告中位数和较慢样本，避免只展示最快一次。
- [ ] 日志仅记录必要标识和耗时，不记录令牌、密钥或完整签名地址。

### 3.3 MP4 分段与 HLS 对比试验

- [ ] 不预先锁定 HLS。先验证 MP4 按需分段处理，同时以服务器 HLS 输出作为对比方案，再根据双平台实测选择。
- [ ] MP4 方案：通过 HTTP Range 获取索引和必要媒体数据，验证能否分段处理后持续提供播放器可识别的 MP4 字节范围，而非等待整集完成。
- [ ] HLS 方案：首批可播放分片就绪后开播，服务器继续接收和处理后续内容。
- [ ] 优先使用流复制，不默认进行实时重新编码。
- [ ] 验证输入 MP4 索引位置、源站 Range 支持、关键帧间隔、加密样本信息和编码兼容性，确认是否能真正提前输出。支持 Range 不等于任意字节段都能独立解密或播放。
- [ ] MP4 方案验证输出索引与媒体偏移、Range 长度与响应语义、读取尚未就绪数据时的等待及错误处理。
- [ ] HLS 方案只公开完整写入的分片；播放列表更新、请求等待、失败结束和重试行为明确，避免半成品分片和反复 404。
- [ ] 验证媒体、播放列表与分片鉴权、HTTPS、过期及访问隔离，特别检查两端子资源请求是否正确携带鉴权。
- [ ] 验证尚未生成位置的进度拖动：不能假装整集可立即任意跳转；必要时重新准备目标位置或明确等待状态。
- [ ] 选择不同长度、编码及索引布局的样本，对比现有整集方案、MP4 分段方案、HLS 方案的首帧、跳集、拖动、弱网恢复和服务器资源成本。
- [ ] Android ExoPlayer、iOS AVPlayer 分别验证；其他项目的 Android 实测不作为 iOS 可行性的证明。
- [ ] 保留原整集方案作为回退，以开关控制上线范围。

分片长度、首播所需分片数量与切换阈值由实测确定。不承诺固定秒开，不把任意切割 MP4 当成可播放分片。

### 3.4 当前播放优先与预加载

| 场景 | 计划行为 |
|---|---|
| 首次打开或跳到未缓存集数 | 优先准备该集开头，首批媒体就绪后开始播放 |
| 正常观看 | 当前播放稳定后，准备下一集 |
| 已准备好下一集 | 直接接管预加载播放器 |
| 快速连续滑动 | 动画跟随，最终选定后准备目标集；取消或降级过时任务 |
| 当前集缓冲 | 暂缓下一集预取，优先当前播放 |
| 进入后台或退出播放 | 停止无用预取，释放备用播放器和请求资源 |

- [ ] 最多两个原生播放器：当前播放一个、下一集暂停待命一个。
- [ ] 默认只准备下一集，不连续预取多集。
- [ ] 下一集开头以约 5～10 秒为初始缓冲目标；当前集由原生播放器管理，以稳定播放为先。
- [ ] Android、iOS 分别调节缓冲；秒数是目标，不保证原生播放器能精确限制。
- [ ] 服务器实现前台任务优先、相同内容请求合并及有界队列。
- [ ] App 取消与服务器任务取消联动；共享任务仍有观看者时不误取消。
- [ ] 明确中断、重试和旧请求失效规则，防止旧结果覆盖当前集、串集或重复播放声音。

### 3.5 缓存与资源预算

- [ ] 手机磁盘视频缓存先设 150MB 上限，支持手动清理和自动淘汰。
- [ ] 内存不保存整集视频；手机不承担片源解密、转封装或重新编码。
- [ ] 当前集与下一集优先保留，正在读取的内容不在使用中删除。
- [ ] 使用不参与系统备份的缓存目录；退出账号或清理缓存时按需删除。
- [ ] 缓存身份包含来源、剧集、分集、清晰度和必要的媒体版本；正确处理资源过期。
- [ ] 服务器分片优先使用临时磁盘，设置容量、过期、并发与 FFmpeg 进程上限，并回收失败任务。
- [ ] 同时观察播放器缓冲与自建缓存，避免重复下载和重复占用磁盘。
- [ ] 低电量、蜂窝网络、设备发热时的降级策略留待实测后确定，先不增加复杂自动规则。

### 3.6 HONGGUO_API 研究线索与验证边界

参考：[HGTV 的 HONGGUO_API.md](https://github.com/pan8664716/HGTV/blob/main/docs/HONGGUO_API.md)。这是第三方客户端研究记录，不是官方开放 API 文档。查阅时原链接及 raw 链接返回 404，以下依据搜索引擎保留的文档内容；不能保证其最新性或完整性，也不据此认定我们当前接口失效。

| 研究线索 | 待验证优化 | 验证边界 |
|---|---|---|
| 按 Range 读取媒体 | 先获取索引和开头数据，降低整集等待 | 必须结合媒体加密结构、输出格式和两端播放能力验证，见 3.3 |
| 视频地址由接口动态返回 | 按有效期复用，失效后重新解析；合并相同集数的取址请求 | 不长期保存或写死带签名 CDN 地址，不无限重试同一失效地址 |
| HTTP 200 空响应、设备身份及接口变化 | 区分空响应、业务拒绝、超时和媒体处理慢，减少无意义重试 | 当前设备身份、接口路径和版本组合需独立核实，不直接套用他人参数 |
| 多个 API 入口 | 验证兼容后做有限次数的故障切换 | 不假定所有路径在各入口均可用，不假定换入口一定更快，不据域名猜测部署位置 |
| 编码兼容性差异 | 在各清晰度下选择两端可播放的编码，减少黑屏和初始化失败 | Android 与 iOS、不同设备分别验证；分辨率相同不代表编码支持相同 |
| 弹幕时间窗口 | 后续按观看位置加载并限量预取，降低初始请求量 | 真实接口及时间戳验证后再接入，不阻塞视频开播 |

- [ ] 将上游响应分类和各阶段耗时关联，避免把接口拒绝或空响应误判为缓冲不足。
- [ ] 对可重试错误采用有上限的重试与退避；对明确失败采用重新解析、兼容入口切换或可读错误提示，策略以实测为准。
- [ ] 每项线索记录样本、平台、测试时间和结果，验证后才标记可采用，不承诺提速幅度。

## 七、架构与双平台验收

Flutter 共用播放状态、观看意图、切集、预加载调度及缓存规则；通过独立原生适配层处理 Android ExoPlayer 和 iOS AVPlayer 的差异。先评估现有插件，确有缺口再扩展原生能力，避免播放器页面继续堆积平台判断。

| 验收维度 | Android 与 iOS 均需覆盖 |
|---|---|
| 开播与切集 | 冷启动、未缓存跳集、已预加载连播、重复进入缓存集数 |
| 交互正确性 | 快速连续滑动、进度拖动、选集、清晰度与倍速切换 |
| 异常恢复 | 慢网、断网重连、片源失效、分片失败、服务器重启 |
| 生命周期 | 前后台、音频中断、锁屏、退出播放、再次进入 |
| 稳定性 | 长时间观看、内存稳定、播放器与任务不泄漏、无后台多路声音 |
| 资源成本 | 流量、磁盘上限、耗电和发热；服务器 CPU、内存、磁盘与带宽 |
| UI 与无障碍 | 清屏、底部安全区域、字体缩放、深浅色及系统辅助设置 |

模拟器用于功能和布局检查，性能结论需结合双平台真机。验收目标是缩短未缓存内容首帧等待、保持快速连播、快速跳集不积压任务、长时间观看资源稳定。具体时间和资源阈值先测基线再确定，不用单次最快结果承诺秒开。

## 八、本轮暂不纳入

- 连续预加载多集、无上限离线下载。
- 手机端片源解密、转封装和实时重新编码。
- 服务器多档实时转码、尚未验证的自适应码率承诺。
- 弹幕发送和完整账户、审核系统。

后续每批完成时，更新本文件的状态、实测结果、已知限制及对应 APK / IPA 版本。未完成的条目继续保留，不因测试包发布而自动标记完成。
