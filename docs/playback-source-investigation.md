# 取源空响应排查（2026-10-27）

## 已确认根因与修复

### 请求频率假设专项对照（2026-10-27）

用户提出“新身份没有历史，连续请求耗尽信誉而被静默拒绝”。本轮保持一组正常匿名注册身份、同一本机网络出口配置、相同客户端协议配置、签名分支 0，固定两个分集交替解析；关闭探针的身份恢复，不下载视频，不更改生产配置。未逐次核验上游实际看到的出口 IP，因此不据此宣称 IP 已被完全排除。

| 阶段 | 调度 | 取源成功 |
|---|---|---|
| 低频基线 | 每次结束后等 5 秒 | 4/4 |
| 连续请求 | 每次结束后等 1 秒 | 6/6 |
| 休息后低频 | 静置 30 秒，再按 5 秒间隔 | 4/4 |

共 14 次取源，包含 14 次播放模型 POST、14 次 fallback GET，全部成功。首末请求相距约 74 秒；任意 30 秒窗口内最多 10 次模型 POST、20 次上游请求。全程同一身份、无自动注册恢复；首次取源直接发生在正常注册后，没有额外的“暖机”请求。证据 `artifacts/performance/identity-rate-control.json`，工具 `tools/probe-identity-rate.cjs`。

另用先前失败的旧注册身份复查，仍为 HTTP 200、0 字节；未重新注册该旧身份。这排除了“休息这段时间就必然恢复”的说法，不能证明永久失效或某一种封禁机制。

代码和部署审计：

- 播放使用持久化注册身份；目录/详情使用另一份进程内 metadataDevice；搜索当前每次构造身份。因此“目录的全部请求都累计到同一个播放 device_id”不符合当前代码。
- 后台索引源码确有最多 120 次、默认 300ms 间隔的批量目录路径，但生产 `ZOVV_INDEX_ON_START=0`，代码据此关闭整段索引采集。它是需要防止误开启的潜在请求源，不能当作本轮实际发出了 50 次 feed 的证据。
- 旧日志缺少完整的逐身份、逐次上游计数，无法从切集次数倒推出历史请求总数；App 缓存命中和预加载接管也不等于重新向上游取源。

结论：身份相关的有效状态/准入差异已有对照证据；本次正常范围内的连续请求没有复现立即拒绝。信誉分、唯一风控主键、初始分值以及“请求越多必然越差”仍不是已知事实。小样本也不能排除更高频率、累计调用量、长时间使用或身份与 IP 联合限制。

建议优先持久化真实注册配置，明确各接口身份与协议配置的来源，补齐不含明文 ID 的请求计数和成功/失败时间线，再进行时间与次数的长窗口对照。不要把固定 3～15 秒、一次暖机或增加身份数当成已验证解决方案。本轮只读审计和诊断探针未更改生产调度。

### 后续发现：已注册身份也会被拒绝

初次注册恢复不等于身份长期有效。用户再次报告失败后，保留原身份做对照：约 29 分钟前注册的身份已返回空正文，同集的新注册身份恢复约 24KB 模型。无法从空正文断言平台的内部拒绝原因或固定有效期，不能把“约半小时”当作已知 TTL。

已补有界恢复：只在播放模型连续两次空正文、且现身份使用超过 10 分钟时尝试一次正常注册；普通超时、媒体错误、限流及年轻身份不触发。10 分钟是防止频繁注册的本地保护阈值，不是平台有效期。并发恢复合并，保存新身份后再请求片源，不无限换身份。

安卓测试特意从旧的失效测试身份启动，实际记录 `playback_identity_recovered`，第 13 集恢复首进度 4417ms，随后画面播放至 0:52；截图 `source-recovered-after-expiry.png`。服务器也部署了恢复逻辑，公网 MP4 / 206 校验通过，服务日志确认恢复了使用约 29.7 分钟的旧身份。网关回归更新为 39 项通过。

### 初始根因对照

当前播放请求使用的 iid/device_id 是本地随机生成的，没有经过匿名设备注册；这组身份不被播放接口接受，服务端以 HTTP 200、0 字节正文表现拒绝。改用正常注册下发的设备身份后，保留原接口、原请求体和原签名算法即可恢复。**旧路径失效不是此次已经验证出的原因，先前基于旧文档的推断应据此纠正。**

控制实验使用同一集和同一旧播放路径：

| 身份配置 | 结果 |
|---|---|
| 原随机身份 | HTTP 200，0 字节 |
| 注册身份，不带 Cookie | HTTP 200，23548 字节，有效模型与媒体解析成功 |
| 随机身份，加注册 Cookie | HTTP 200，0 字节 |
| 注册身份与 Cookie 配套 | HTTP 200，23732 字节，有效模型与媒体解析成功 |
| 与注册身份相同位数的新随机身份 | HTTP 200，0 字节 |

注册身份下，新 `video_model/v1/` 同样返回有效模型；因此也不能把“换新路径”当作本次恢复的决定因素。上述实验不能读取服务端内部规则，但足以将实际修复定位到身份准入，而不是 Cookie、HTTP/2、下载、转封装或手机解码。

## HONGGUO_API 文档与代码差异

来源：https://github.com/pan8664716/HGTV/blob/main/docs/HONGGUO_API.md

原页面和 DEVICE_REGISTER.md 当前直接访问均为 404。本轮读到的是搜索引擎保留的正文（显示约三日前抓取）；其中接口变更记录日期为 2026-10-14，不能当成今天的官方可用性保证。

| 项目 | 当前实现 | 文档记录 |
|---|---|---|
| 播放路径 | `/novel/player/multi_video_model/v1/` | `/novel/player/video_model/v1/` |
| 请求体 | `mixed_video_id_map` 批量映射 | 单值 `video_id`，并可带 `biz_param` |
| 模型位置 | `data[vid].video_model` | `data.video_model` |
| 设备身份 | 进程内随机生成 iid/device_id，无注册生命周期 | 注册后持久化使用成对身份 |
| 签名分支 | 最多尝试 32 次，接受 0 或 2 | 最多 128 次，只接受 0 |

上述是确认存在的适配差异，不等同于已经证明某一个差异就是本次故障的唯一原因。文档关于随机身份播放准入的描述本身带有历史实测条件，应以当前响应重新验证。

## 已执行的验证与边界

1. 在独立 VM 探针中更改路径、单值请求体、模型取值以及分支 0，正式取源代码未变。
2. 另测最简 `video_id` 请求体，包含文档样例集数；仍为 HTTP 200、0 字节。
3. 新路径使用 b、a、c、lf 四个官方入口的有限探针均为空，不能认为换一个域名即可恢复。
4. 旧版本 71332 与 72232/73532 请求配置的小样本也未恢复，不将未经验证的版本号切换写入正式逻辑。

结论：当前共同依赖的播放模型请求被返回空正文。旧协议适配及设备准入/签名兼容是优先核查方向；无法从空正文中区分具体拦截原因，也没有业务错误码证明某个设备已被封禁。不能宣布平台整体停服、接口永久关闭或已经修复。
